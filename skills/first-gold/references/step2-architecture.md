# 第 2 步：搭架构

目标：先把交互想清楚，再让 AI 开发；开发时拆成一个个最小闭环，单独做、单独验证。

## 为什么顺序不能乱

最开始就要把需求和背景跟 AI 说清楚，**先做出整体的 UI 交互原型，再让它深度开发**。不然 AI 一上来就建数据库、写后端，生成一大堆你觉得没意义的文件，非常浪费时间和 token。

顺序：

1. 得到一套完整的交互 UI 图
2. 做出一个可交互的前端 demo，确认整体流程是你想要的
3. 最后才让 AI 真正去开发

第 3 步通常最耗 token，所以前两步一定要小步迭代。

## 2a. UI 图

先问用户：

- 用户打开产品后，第一眼看到什么？
- 从打开到拿到结果，一共要经过哪几页？每页做什么操作？

列出 3–5 个关键页面和它们之间的跳转，再出图。可选的做法：

- 让 AI 直接写一个只有布局、不带功能的 HTML 线框
- 用 AI 画图工具出几张界面效果图
- 用 Figma、Lovable、v0 这类工具快速出界面

产出：UI 图（截图或链接）+ 页面流程，写进 `02-架构.md`。

## 2b. 可点击的前端 demo

- 一个 HTML 文件就够，用写死的假数据，不接任何后端
- 每个按钮都要能点，能从第一页走到最后一页
- 让用户自己完整点一遍，问他：“这个流程是你想要的吗？哪一步别扭？”
- 改到用户确认为止，再进入开发

产出：demo 文件或链接，以及“用户已确认流程”的记录。

## 2c. 拆成最小闭环，一个一个开发

把完整功能拆成几个小闭环。每个闭环都要能单独开发、单独验证，做完一个就是一个可以用的进展。

**例子**：想做一个“投递简历就能自动找到对应面经”的工具，可以拆成：

| # | 闭环 | 输入 | 输出 | 怎么验证 |
|---|---|---|---|---|
| a | 分析简历，推断适合的岗位方向 | 一份简历 | 3 个岗位方向 + 关键词 | 拿 3 份不同的简历试，结果合不合理 |
| b | 抓取对应的小红书面经帖子 | 关键词 | 10 篇帖子的标题和正文 | 打开原帖核对内容 |
| c | 信息匹配：把面经和简历对上 | a 和 b 的结果 | 一份按相关度排好的面经清单 | 自己读一遍，前 3 篇是不是最有用 |

不拆开做，很可能烧了很多 token，最后 demo 还是没做出来。

**开发时的习惯**：

- 一个闭环开一次新对话，只给 AI 这个闭环需要的上下文
- 每做完一个，在 `02-架构.md` 里把状态改成“已完成”，并记下踩过的坑
- 先让闭环 a 跑通，再做 b，不要三个一起开工
- 抓取第三方平台内容（比如小红书）要遵守平台规则：少量、个人用途，能用官方接口就用官方接口

```markdown
| 2 | | | | | |

## 踩过的坑
-
```

## 过关标准

- 有 UI 图
- 有可点击的 demo，并且用户确认了流程
- 最小闭环至少 3 个
- 第一个闭环已经跑通
